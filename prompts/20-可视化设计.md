# 可视化设计指引 —— 什么时候自制图、怎么写规格

> 目标:让抽象的地方"一看就懂",同时**一个像素都不超出原文**。

## 一、先判断:这里到底需不需要自制图?

| 原文特征 | 处理方式 |
| --- | --- |
| 原文已有拓扑图,且图能说明问题 | 直接引用原图(`figures`),写好中文讲解,**不要重复画一遍** |
| 报文/消息一步步传递,或状态逐步推进 | `packet_flow`(动画 + 分步静态图) |
| 判定流程、层级结构、时序交互 | `mermaid` |
| 状态机、树、有环的关系图 | `graphviz` |
| "A 和 B 有什么区别""什么时候用哪个" | `comparison_table` |
| 极抽象的概念,需要生活类比才能理解 | `ai_illustration`(每章最多 1 个,能不用就不用) |
| 原文一句话就能说清 | **不画图**。图不是越多越好 |

一章建议 2~4 个自制图。**宁缺毋滥**:每个自制图都要能回答"原文哪句话难懂"。

## 二、共同要求(所有 kind)

```json
{
  "id": "v1",
  "kind": "packet_flow",
  "title_zh": "图标题:说清这张图讲什么",
  "why_zh": "原文只用一句话说明 X,没有展示 Y 的过程,初学者不容易想象",
  "caption_zh": "图下方的一句话总结(可留空)",
  "source_pages": [4],
  "grounding": [
    "支撑本图的英文原文引用 1(逐字复制)",
    "支撑本图的英文原文引用 2"
  ],
  "spec": { }
}
```

- `why_zh` 必须指出**原文的哪个点抽象**,不能写"为了更好理解"这种废话。
- `grounding` 里每一条都会被拿去和原文做模糊比对(阈值 88)。
  **图里出现的每个节点名、每条链路、每个步骤,都要在 grounding 里有出处。**

## 三、`packet_flow`(主力,渲染成动画 GIF + 分步静态图 + MP4)

### 规格

```json
{
  "nodes": [
    {"id": "R1", "label": "R1", "role": "router", "x": 0.0, "y": 0.5, "sublabel": "DR"},
    {"id": "R2", "label": "R2", "role": "router", "x": 1.0, "y": 0.5}
  ],
  "links": [
    {"from": "R1", "to": "R2", "label": "Gi0/1"}
  ],
  "steps": [
    {
      "title_zh": "R1 发出 hello 报文",
      "note_zh": "这一步在原文里对应的说明(仍须来自原文)",
      "packets": [{"from": "R1", "to": "R2", "label": "hello"}],
      "highlight_nodes": ["R1"],
      "highlight_links": [["R1", "R2"]],
      "state": {"R1": "Init"}
    }
  ]
}
```

### 字段说明

| 字段 | 说明 |
| --- | --- |
| `nodes[].role` | `router` / `switch` / `host` / `server` / `cloud` / `firewall`,决定画成什么图标 |
| `nodes[].x` `y` | 0~1 相对坐标。`x=0` 最左、`x=1` 最右;`y` 相同的节点会排在同一行。不填则自动横向均分 |
| `nodes[].label` | 节点上的名字,必须是原文或原文拓扑图里出现过的(如 `R1`、`SW2`) |
| `nodes[].sublabel` | 节点下方小字(角色/地址),可选 |
| `links[].label` | 链路上的小字(接口名、网段),可选 |
| `steps[].packets` | 该步骤中在链路上移动的报文;`label` 是报文名,要用原文的叫法 |
| `steps[].highlight_nodes` | 本步骤要高亮(变橙色)的节点 |
| `steps[].highlight_links` | 本步骤要高亮的链路,写成 `[["R1","R2"]]` |
| `steps[].state` | 节点上方的状态气泡,如 `{"R1": "Full"}`;用来表现状态迁移 |

### 经验

- 步骤数 3~8 步最好读。少于 3 步不如直接写文字,多于 8 步应拆成两张图。
- 一个步骤里的 `packets` 可以有多个(表现"同时发送")。
- 表现"没有报文,只是状态变了"的步骤:`packets` 留空数组,只给 `state`。
- 节点不要超过 6 个,否则图会挤。
- `title_zh` 是步骤标题,要写成动作句("R1 发出 hello 报文"),不要写成名词("hello 报文")。

## 四、`mermaid`

```json
{"spec": {"code": "flowchart LR\n    A[收到 BPDU] --> B{优先级更低?}\n    B -- 是 --> C[更新根桥]\n    B -- 否 --> D[丢弃]"}}
```

- 常用:`flowchart LR/TD`、`sequenceDiagram`、`stateDiagram-v2`。
- 装了 `mermaid-cli` 会渲染成 PNG;没装就在笔记里内联 mermaid 代码块,
  Obsidian / Typora / VS Code / GitHub 都能正常显示,**不影响可读性**。
- 节点文字可以用中文,但协议名/状态名保留英文。
- 不要在 mermaid 里塞长段落,超过 20 个字就换成 `packet_flow` 或表格。

## 五、`graphviz`

```json
{"spec": {"dot": "digraph G {\n  rankdir=LR;\n  node [shape=circle];\n  Down -> Init [label=\"hello received\"];\n  Init -> \"2-Way\" [label=\"sees own router ID\"];\n}"}}
```

装了 `graphviz` 渲染成 PNG,没装则内联代码块。

## 六、`comparison_table`

```json
{"spec": {
  "headers": ["对比项", "OSPF", "EIGRP"],
  "rows": [["协议类型", "链路状态", "距离矢量"]]
}}
```

表格里的每一格都要能在原文找到依据。**不要用表格塞进原文没有的对比维度。**

## 七、`ai_illustration`(谨慎使用)

用于"原文概念极其抽象,必须靠生活类比才能建立直觉"的场合。

```json
{"spec": {
  "prompt_en": "A simple metaphor diagram showing a postal sorting office deciding which of two roads a letter should take",
  "must_include_labels": ["R1", "R2", "Route A", "Route B"],
  "style": "clean flat vector technical diagram, white background, no photorealism",
  "negative_prompt": "extra text, logos, watermarks, 3D rendering"
}}
```

规则:

- `must_include_labels` 是**图中唯一允许出现的文字**,而且这些文字必须来自原文。
- 生成后会自动打上"AI 辅助示意图 · 非 PDF 原图"水印,笔记附录也会声明。
- 需要在配置里把 `illustration_provider` 设为 `gemini` 或 `openai`,并设置 API Key 环境变量;
  未配置时工具会**跳过生成但保留提示词**,笔记里给出提示,不会报错中断。
- 因为它不可控,**优先用前四种**。前四种能表达的,一律不要用它。
