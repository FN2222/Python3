# 费曼测验设计指引 —— 章末怎么检验学习成果

## 一、费曼学习法在笔记里的四步落地

| 费曼原步骤 | 笔记中的字段 | 作用 |
| --- | --- | --- |
| 1. 把它讲给外行听 | `feynman.explain_back_zh` | 提供一份"大白话复述范本",读者照着自己讲一遍 |
| 2. 找出讲不下去的地方 | `feynman.questions` | 用题目逼出盲点 |
| 3. 回到原始材料补齐 | 每题的 `source_pages` + `evidence_quote` | 直接指回原文第几页,不用翻书找 |
| 4. 简化并重讲 | `feynman.blind_spots_zh` + `review_plan_zh` | 提炼易错点与复习节奏 |

## 二、`explain_back_zh` 怎么写

- ≥ 80 字,建议 150~300 字。
- **像跟人说话**:用"先……然后……如果……就……"的顺序讲清主线。
- 少用术语。必须用的术语,顺带一句解释。
- 只能用本章原文提到的元素做类比,不能引入原文之外的比喻对象。

反面例子(不合格):

> 本章介绍了 OSPF 邻居邻接关系的建立机制,包括 hello 报文的作用、邻居状态机的迁移
> 以及 DR/BDR 选举算法。

—— 这是目录,不是"讲给外行听"。

正面例子:

> 两台 OSPF 路由器要合作,得先互相打招呼。它们在链路上不断发 hello 报文,
> 广播网段上这个报文发到 224.0.0.5,每 10 秒一次。收到之后还要核对四样东西……

## 三、题目要求

### 3.1 数量与结构

- 默认 8~20 题(具体阈值见任务包的 `TASK.md`)。
- `type` 至少覆盖 `concept`(概念)和 `process`(过程);
  有配置/命令的章节应有 `config` 题,有对比的章节应有 `compare` 题。
- `difficulty` 按 1 → 3 递进排列,别把难题全堆在最后。

| type | 中文标签 | 适用 |
| --- | --- | --- |
| `concept` | 概念 | "X 是什么""X 的作用是什么" |
| `process` | 过程 | "X 是怎么一步步发生的" |
| `compare` | 对比 | "X 和 Y 有什么区别" |
| `config` | 配置 | "用哪条命令""这条命令的输出说明什么" |
| `troubleshoot` | 排障 | "出现现象 A,原文说可能是什么原因"(**原文必须真的讲过这个原因**) |
| `calculation` | 计算 | "默认值是多少""是几倍关系" |

### 3.2 中英双语要求

- `q_zh` / `q_en` 必须是**同一道题**的两个语言版本,不能各问一件事。
- `answer_en` 尽量贴合原文表述(可以是原文句子的整合);`answer_zh` 是它的中文版。
- `q_en` / `answer_en` **不能混入中文字符**;`q_zh` / `answer_zh` 必须含中文。
  工具会检查这一点。

### 3.3 不超纲(硬要求)

- 每题必须填 `evidence_quote`:答案所依据的英文原句,逐字来自原文。
- `source_pages` 必须是**正文小节已经讲过的页**。
  如果你想考的内容正文没写,那就先把正文补上,而不是直接出题。
- 禁止出现:原文没给的默认值、原文没提的命令参数、原文没讨论的场景。

### 3.4 `scoring_points_zh`(自评要点)

写成可勾选的检查项,让读者能自己判分:

```json
"scoring_points_zh": ["说出 hello interval 和 dead interval", "说出 area ID", "说出子网掩码"]
```

## 四、`blind_spots_zh`

写"最容易记错/漏掉的点",而且必须是本章原文里真实存在的细节。例如:

- 容易只记住 hello interval 要一致,忘了 dead interval、area ID 和子网掩码也必须一致。
- 容易把 2-Way 的触发条件记成"收到 hello 报文",实际上是"在对方的 hello 报文里看到了自己的 router ID"。

不要写"要多做实验""要理解本质"这类空话。

## 五、`review_plan_zh`(可选)

给出 2~3 条具体的复习动作,例如:

- 第 1 天:合上笔记复述邻居状态的四个阶段与触发条件。
- 第 3 天:只看拓扑图,讲一遍 DR 选举的判定顺序。
