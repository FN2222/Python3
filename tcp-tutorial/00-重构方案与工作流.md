**I. 重传与恢复（第 10–13 章）**

## Step 11：需要增加哪些实验

全部实验基于 Linux network namespace + veth + tc netem，可在单机复现（详见附录 A）：

1. **EXP-01 基线传输**：无损耗 10ms RTT，iperf3 单流，观察 Slow Start → CA（第 7、8 章）
2. **EXP-02 高 RTT**：netem delay 100ms，观察 BDP 与窗口限制（第 2、19 章）
3. **EXP-03 小 rwnd**：`SO_RCVBUF`/`tcp_rmem` 压小，观察 Window Full / rwnd-limited（第 4、19 章）
4. **EXP-04 Zero Window**：接收端故意不读 socket，观察 Zero Window / Probe / Update（第 4 章、综合案例 5）
5. **EXP-05 单包丢失**：netem loss 0.5% 或 iptables 精准丢包，观察 Dup ACK / SACK / Fast Retransmission（第 9、10 章）
6. **EXP-06 尾包丢失**：drop 最后一个 Segment，观察 TLP / RTO（第 12 章对比实验 Case B）
7. **EXP-07 持续丢包**：netem loss 2%，观察 Fast Recovery 与吞吐坍缩、Mathis 公式验证（第 11、19 章）
8. **EXP-08 乱序**：netem reorder，观察 Dup ACK ≠ 丢包、D-SACK、RACK reordering window（第 9、13 章）
9. **EXP-09 cwnd 观测**：`ss -ti` 每 100ms 采样画 cwnd 曲线，与 Wireshark Bytes in Flight 对照（第 6、17 章）
10. **EXP-10 拥塞算法对比**：cubic vs bbr 在同一 netem 剖面下的吞吐/重传对比（第 14 章）
11. **EXP-11 Offload 对比**：开/关 GRO、TSO 前后抓包对比超大 Segment（第 18 章）
12. **EXP-12 双点抓包**：在 veth 两端同时 tcpdump，用 Seq 追踪定位人为丢包点（第 20 章、综合案例 7）

## Step 13：哪些地方必须使用 ss / tcpdump / tshark / eBPF

| 场景 | 工具 | 原因（为什么 Wireshark 不够） |
|---|---|---|
| 读取 cwnd/ssthresh/rto/pacing_rate/delivery_rate | `ss -ti` | 这些是 TCP Stack 内部状态，不出现在报文中 |
| 服务器无 GUI 抓包 | `tcpdump -w` | 生产服务器通常无图形界面 |
| 批量统计重传/RTT | `tshark -T fields` | 脚本化统计比 GUI 快 |
| 定位内核丢包点 | `bpftrace`/BCC `tcpdrop` | 丢在内核里的包 Wireshark 在 tap 点之后看不到 |
| 观察每次重传事件及当时状态 | BCC `tcpretrans` | 能带出触发时的内核状态，抓包只能事后推断 |
| 长期低开销监控 | eBPF + tcp tracepoints | 全量抓包在高带宽下不可行（capture loss） |

## Step 14：设计最终综合案例

综合案例 8（第 23 章）把全部机制整合进**一条** TCP 连接：跨地域大文件下载（Client 东京 ← Server 新加坡，RTT 70ms，瓶颈 200 Mbps），路径中转发设备在两个时刻分别制造"中间丢包"（触发 Dup ACK/SACK → Fast Retransmission → Fast Recovery/PRR）与"突发静默丢包 + 尾丢"（Dup ACK 不足 → TLP → RTO → cwnd 归 1 → 重新 Slow Start）。全程提供：三次握手（MSS/WS/SACK-Permitted）→ IW10 起步 → Slow Start 逐 RTT 推演 → 到达 ssthresh 进入 CA → 第一次丢包与恢复 → 第二次 RTO → 再恢复。配 10 类图 + 双点抓包 + `ss -ti` 采样 + 9 环节证据链 + Before/After 表。综合案例 1–7（第 22 章）分别覆盖案例类型 A–H（CDN、跨地域、对象存储、移动网络、Zero Window、数据中心、多点定位）。
