# 第 23 章 最完整综合案例（综合案例 8）：一条 TCP 连接的完整追踪与证据链

> **【教学模拟案例·可复现】**（附录 A EXP-12 完整脚本；机制行为按 2026 年 Linux 默认栈：CUBIC + RACK-TLP + PRR + SACK + HyStart + pacing）。本案例是第 15 章大联动的"排障版"：同一条连接，这次以生产值班视角，从故障工单出发，走完 Phase 1–9 与九环证据链，并附全部六类图与多点抓包定位。

## 0. 工单

> "新加坡对象存储向东京客户端分发 200MB 模型文件，下载时快时慢，偶尔卡住几百毫秒。请排查网络。"

## 图 1：网络拓扑与抓包点

```
Client(东京, Linux) ──[A: Client主机 tcpdump]── 接入SW ── FW ──[B: FW外侧镜像]──
```

参数（握手实测）：MSS=1460、WS=7/7、SACK_PERM、rwnd 上限 512KB、Server IW=10、CUBIC。

## Phase 1 故障现象

单次下载吞吐曲线：爬升 → 稳定 ~87Mbps → 中途一次短暂下探（~2.0s 处）→ 恢复 → **4.0s 处一次 ~300ms 完全停顿** → 再爬升恢复。用户感知"卡一下"。

## Phase 2 假设清单

A 带宽不足 / B 高 RTT / C 丢包 / D rwnd / E cwnd / F Server 应用 / G Client 应用。

## Phase 4 排除

- **D rwnd**：图 5 rwnd 全程平直 512KB，无 ZeroWindow/WindowFull（filter 计数=0）⇒ 排除。
- **G Client 应用**：Client 读取无积压（Recv-Q≈0），Ack 及时 ⇒ 排除。
- **B 高 RTT**：40ms 基线不变，属设计内（BDP 已由窗口覆盖）⇒ 排除为"根因"（是背景参数）。
- **F Server 应用**：D 点 `notsent` 在 4.0s 前短暂为 0（供数抖动），但停顿主体 296ms 远超供数缺口 ⇒ 供数抖动是**诱因**（让在途只剩 3 段）而非停顿本体。
- **A 带宽不足**：稳态 87Mbps 接近瓶颈额定，多流验证可达 97 ⇒ 排除。
- 剩余：**C 丢包（两次，两种形态）+ E cwnd（作为丢包后果）**。

与骨干设备计数器对帐：C 侧上游 POP 端口在 2.0s、4.0s 对应时刻有微突发丢弃记录。

## Phase 6 进一步定位（两次事件为何形态不同）

- 事件一：单段丢失、在途 ~300 段 ⇒ Dup ACK/SACK 充足 ⇒ RACK/3DupACK 判丢 ⇒ **Fast Retransmission + PRR**：吞吐只降到 61Mbps、零停顿。
- 事件二：供数抖动使在途仅 3 段，突发劣化把 3 段+TLP 探测全丢 ⇒ **无任何反馈可用** ⇒ RTO 兜底：296ms 静默 + cwnd=1 + 重新 Slow Start——用户感知的"卡住"即此。
- 同一条链路、同一类丢包，**在途数据量的多寡决定了恢复代价差两个数量级**（第 12 章对比表的活例）。

## Phase 7 根因

骨干 POP 端口微突发拥塞丢包（外因）；叠加 Server 供数抖动造成的小在途窗口，使第二次丢包落入"Dup ACK 盲区"，以 RTO 形态放大为用户可感知停顿（内因放大器）。

## Phase 8 修复

① 运营商/骨干侧：修正该 POP 队列/整形配置（消除微突发丢弃）；② Server 侧：修复供数抖动（预读缓冲），并确认 TLP/RACK 参数为默认最新；③ 监控侧：为 `TCPTimeouts`、分段丢包率建立告警。

## Phase 9 修复后验证

复测 20 次下载：无 RTO 事件；FastRetx 偶发（<5/次）；吞吐曲线平滑。

## 完整证据链（九环）

```
证据1  RTT基线40ms平稳（tcptrace RTT图）           → 排除时延型根因
证据2  rwnd全程512KB平直、零ZeroWindow/WindowFull   → 排除接收侧
证据3  事件一出现连续DupACK（8002-8004）            → 有段未按期到达
证据4  SACK块右沿逐帧扩张(24091461-…)              → 后续段均到达，缺口唯一
证据5  同Seq=24090001再次出现(8005)                 → 发生重传
证据6  8005与DupACK#3零间隔+此前≥2DupACK           → 判定Fast Retransmission
证据7  ss采样: cwnd 300→(PRR)→210, ssthresh=210    → 拥塞响应符合CUBIC β=0.7
证据8  吞吐同步 87→61→87 Mbps（I/O Graph）         → 窗口变化与吞吐因果闭合
多点证据  该段A/B存在、C消失；ACK方向全存活          → 丢包定位于B→C骨干段
（事件二平行链：零DupACK+296ms空洞+同Seq再现+backoff → RTO；三段+TLP在C全消失 → 同段突发丢）
最终定位  B→C 路径微突发丢包；供数抖动放大第二次事件为RTO
```
